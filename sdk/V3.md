# SDK: native UI and mod authoring services

Local settings/status test build: `SWML_V3_CAP_UI_STATIC_TEXT_OBSERVER` observes
native text during rendering as well as input traversal. This covers static labels
such as the version text. With this capability, `ui_watch_rect` accepts height=-1
to ignore measured height while matching every other bound exactly. Widget bounds
set through the normal geometry APIs still require nonnegative height.

## Native UI implementation

The UI service constructs **the game's own** `c_ui_element_text`, `c_ui_element_rectangle_button` and composite containers. It attaches them through the game's child-registration and initialization path. The game's normal UI traversal performs layout, rendering and input dispatch. There is no new SwapBuffers drawing callback, immediate-mode GPU overlay, or mod-owned replacement renderer in this feature.

Supported operations:

- Create native containers, text labels and buttons underneath those containers.
- Query children and find descendants by native class.
- Inspect native dimensions, visibility, enabled state and ownership.
- Change native text, bounds, visibility and button enabled state.
- Receive mount/update/click/unmount callbacks.
- Remove mod-created widgets and automatically reclaim them on screen teardown or watch removal.

Dropdowns, sliders, edit boxes and arbitrary replacement of native virtual methods are not part of this first UI surface. Existing widgets of those classes can still be found as native descendants and have supported base properties inspected/edited; unsupported property operations return errors. Text editing targets text widgets and button captions. The backend does not invent a universal property layout for unknown classes.

## Start a native UI mod

```powershell
python swml/tools/new_mod.py my_ui --output my_ui --native-ui
cmake -S my_ui -B my_ui/build -G "Visual Studio 17 2022" -A x64
cmake --build my_ui/build --config Release -- /m:1 /nodeReuse:false
```

The generated example watches `c_ui_main_menu_interface`, creates a native container with a label and button, and changes the label when the button activates. It starts disabled. It does not modify game rules or add network messages. The complete source is in `examples/sdk_v3_native_ui/`.

A minimal setup is:

```cpp
#include "sdk_v3.hpp"

void screen(const swml_ui_event* event, void*) {
    if (event->kind == SWML_UI_MOUNT) {
        auto d = swml3::ui::description(
            SWML_UI_LABEL,
            {0.05f, 0.05f, 1.2f, 0.15f, SWML_UI_BOTTOM_LEFT},
            "Hello from a native widget");
        swml_ui_handle label = 0;
        swml3::ui::create(event->root, d, label);
        // Retain successful handles in per-root state if subsequent updates need them.
    }
}
bool setup() {
    swml_handle watch = 0;
    return swml3::ui::watch("c_ui_main_menu_interface", screen, nullptr, watch) == SWML_OK;
}
ModSetup registration{setup};
```

## Coordinate and style contracts

Coordinates use native parent-relative UI units, not desktop or framebuffer pixels. Inspect the parent bounds before designing a layout. Anchors 0–8 are top left/center/right, middle left/center/right, and bottom left/center/right. Width/height must be finite and nonnegative; positions must be finite. The API bounds values to a sensible range before native calls.

The descriptor's colors use the native packed color convention. The C++ helper supplies standard background/hover/pressed colors and native text sizing defaults. A button caption is an ordinary native text child.

A container is initially transparent. Its native descendants handle their own graphics. Attach a mod container to an appropriate game container rather than a label or another native control whose drawing/layout overrides do not traverse arbitrary children. The API rejects label parents for widget creation.

## Execution and lifetime

UI mutations are accepted only inside the matching watch's `MOUNT`, `UPDATE` or `CLICK` callback. Otherwise they return `SWML_WRONG_THREAD`. This is a native UI execution context, separate from the SDK's game/render task lanes. Scheduling a render task is not permission to edit native UI. Exchange immutable model snapshots or synchronized state with game/network workers, then apply changes from the UI callback.

Button activation is recorded during the native input method and delivered at the next matching UI update boundary. This lets a click handler destroy its own button without freeing an object whose input method is still executing. Pending clicks for an already destroyed handle are discarded.

Handles are monotonically generated identities scoped to a watch/root instance. The registry never exposes native pointers. Native destruction invalidates aliases and descendants. If the game reuses an address, the next mounted instance gets fresh handles. `UNMOUNT` reports the historical root handle so the mod can clear its per-root state; those handles cannot be used to mutate the dying tree.

`ui_unwatch` can be called from any thread. It stops future callbacks immediately; `SWML_PENDING` means one callback is already running, so keep its context alive until it finishes. Widget cleanup/restoration occurs at the next native update for that root, or through ordinary native destruction. A hidden screen that is not updating may therefore retain its inactive widgets until it updates or is destroyed. Mod DLL hot-unloading remains unsupported.

The game owns its original widgets. They can be inspected/edited but not deleted through this API. A mod can delete only widgets belonging to its own watch. Two watches cannot silently claim the same original widget for mutation: the second receives `SWML_CONFLICT`. Stopping a watch restores its original edits only when the property's current value still matches its last write, preserving intervening game changes.

Native container destruction owns recursive child destruction. SDK cleanup removes only its top-level created objects, then lets native teardown handle their descendants. Object allocation uses the game's allocator/delete path; text temporaries use its separate aligned-string allocation/free path. Constructors consume their temporary strings while the text setter copies its input. Mod authors do not manage those native allocations.

## Commands and logging

```cpp
swml_handle command = 0;
swml3::command("my_mod.status", "Report current state", callback, context, command);
swml3::run("other_mod.inspect", "brief");
swml3::log(SWML_LOG_WARNING, "The requested provider is unavailable");
```

Command names belong to the registering mod's namespace. Commands can be enumerated with their help text. Invocation queues a copied, NUL-terminated UTF-8 argument string to the game lane; `event->sender` identifies the local calling mod. `OK` means queued, not completed. This is a local command registry, not an automatic in-game console, remote RPC or authorization system. Critical commands need explicit results and domain validation.

Structured logging supports debug/info/warning/error and rejects embedded newline injection. `result_name()` provides stable readable text for SDK error codes. Native DLLs are trusted code; these APIs do not sandbox another mod.

## Writable settings

```cpp
swml3::setting(L"display", L"enabled", L"true");
```

Writes target only that mod's INI file. Names/values are validated against malformed keys and line injection. The existing typed readers see the new values. INI writes perform synchronous Windows profile IO; keep them out of repeated per-frame work. Use the atomic blob API for larger mod-owned data. Neither service coordinates a native world-save transaction.

## Dependencies

```ini
[mod]
api=3
depends=inventory_provider, world_rules
optional_depends=diagnostics
```

Dependencies refer to loader directory IDs. Required providers load first. Missing, disabled, API-incompatible, cyclic or failed-to-initialize required dependencies block the consumer with a concrete status. Failure propagates through required chains. Optional dependencies influence order when available; optional cycles never disable otherwise loadable mods.

With no declared dependencies, the loader keeps its prior alphabetical order. Initialization success is the loader-level criterion; consumers must still query the provider's versioned service/capabilities. Dependency version expressions, downloads and automatic installation are not supplied.

## Compatibility and validation scope

The native UI bindings were checked against the archived original and the installed executable **without running either game executable**. The runtime tests use a mock native object backend to verify ownership, conflicts, stale handles, recursive cleanup, attachment failure and callback behavior. They do not establish visual quality, hit testing or gameplay behavior in a live session. No game or computer-use validation was performed for , as requested.

## Resizing panels after editing text

SDK labels created with `rect.height = 0` opt into native auto-height text layout.
Require `SWML_V3_CAP_UI_TEXT_AUTO_HEIGHT` before relying on this behavior. The
wrapped height is then returned by `ui_inspect`; a nonzero creation height retains
fixed-height behavior. This opt-in also makes pagination measurements accurate.
The native constructor's final byte controls whether layout copies its measured
height to the widget bounds. Merely calling layout on a fixed-height label does
not resize it. Existing native tooltip labels already set their own auto-height flag.

Use `swml3::ui::text_in_panel(panel, label, text, bottom_padding, minimum_height)`
for top-anchored labels in tooltips/panels. It sets the text, reads the native reflow
height (including wrapping), and fits the panel to the label's absolute bottom edge.
The panel keeps its native width, position and anchor. Its label must be top anchored
and use the native upward-positive y coordinates. Other labels above it are accounted
for by its y offset. For other layouts, explicitly manage all affected bounds.

Call the helper during UPDATE as well as MOUNT, including when the label already has
the requested text. Native code can reset the background bounds without resetting the
label. Adding `after.height - before.height` only works for the first text mutation;
on later updates that difference is zero. Absolute bounds make fitting repeatable,
allow shrinking and avoid cumulative growth. SDK ownership restores panel/text edits.
The explicit-api overload is `fit_panel_text(api, owner, panel, label, text, ...)`.
